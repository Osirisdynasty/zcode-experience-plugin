# zcode 经验复用体系 v0.2.0 —— 机制、用法与施工手册

> 讲解版 2026-10-12。配套插件包：`zcode_experience_plugin_v0.2.0.zip`（本目录）。
> 本文回答四个问题：zcode 原有机制是啥 → 我们怎么用 zcode → 经验复用体系怎么配这个用法 → 具体每单怎么施工。

---

## 一、zcode 原有机制盘点（体系的地基——哪些是现成的）

### 1. 原始记录：全量留痕的会话数据库（最重要的现成资产）

zcode（ZCode CLI/桌面端）把每次会话完整落盘在 `~/.zcode/cli/db/db.sqlite`，三层结构：

| 表 | 内容 | 规模（本机实测） |
|---|---|---|
| session | 每条会话（id/标题/时间/归档位） | ~290 条 |
| message | 每条消息（角色/时间/语义标注——真人消息 vs 工具合成可区分） | 13,313 条 |
| part | 消息的组成块：文本/工具调用（含完整 input/output/状态） | 52,484 条 |

**关键认知**：殿下架构图里最底层的「事件流（发生了什么）」在 zcode 这里**早已存在且完整**——每个工具调用的输入输出、每次真人插话、每个错误都是可回查的行。10 月初的讨论曾以为「zcode 对话不落盘、会话结束就丢」，实测推翻：**不是没有原料，是原料从来没有被接入经验体系**。这就是本体系的立足点：不新造采集层，直接在只读数据库上做切分与提炼。

### 2. 内建记忆体系（memories/）：结论直存卡片

zcode 自带一套文件式记忆：`~/.zcode/cli/memories/projects/<项目>/memory/`，一文件一事实，`MEMORY.md` 索引每次会话全量常驻 system prompt（本机 154 行/1.1MB 正文）。

它的**病**（也是本体系要治的）：
- **四层混装**：完工记录（其实是经历索引）、坑与判据（其实是经验）、殿下的规矩（memory）、"Mimosa 拦 X 的绕行法"（接近 knowledge）全塞一个目录；
- **全量常驻**：索引只增不减，每条都在抢注意力，与新单 goal 零关联——这就是"调用不知道什么东西"的病根；
- **判决书式写入**：会话收尾一次性压缩成结论，过程（被否决的方案、弯路）不保留——想翻案时无案卷；
- **无治理**：无过期、无验证，"待重启生效"类条目腐化了没人管。

定位：本体系上线后，memories 退回纯 memory 层（用户偏好+活跃工作集+经验库指针），**经历与经验迁出独立成库**。

### 3. 技能通道（skills）：程序性知识的独立载体

`SKILL.md` 文件+自动触发——zcode 体系里唯一原生做了"knowledge 分层"的部分（怎么做某类事的方法论）。经验体系不替代它：skill 管"稳定成型的操作法"，经验管"带适用条件的判断增量"。

### 4. 插件机制（plugins.dirs）：命令+技能+钩子三件套

`~/.zcode/cli/config.json` 的 `plugins.dirs` 列表里放插件目录，重启即载。一个插件可同时提供：
- **命令**（commands/*.md，用户可输入的斜杠命令）
- **技能**（skills/，自动触发的方法论）
- **钩子**（hooks/hooks.json，生命周期事件挂脚本）

经验复用体系本身就是一个插件（`experience`），走的就是这条路。

### 5. 钩子机制（hooks）：确定性脚本的自动挂点

生命周期事件（SessionStart/Stop/PreToolUse/PostToolUse/UserPromptSubmit…）可挂任意进程脚本。本体系用 **Stop 钩子**做归档兜底（会话结束自动查缺）。

### 6. 上下文压缩：会话内自动摘要

长会话被 harness 自动摘要续窗——但它不持久、跨会话不留。归为"会话内 summary 层"，与跨会话经验无关，不冲突。

## 二、我们怎么用 zcode（用法决定设计）

zcode 在殿下的智能体舰队里的用法有四个特征，每个都直接塑造了经验体系的设计：

**1. 工单制（离散单生命周期）**。zcode 不驻留——拉起即满负荷干活，干完即散。时间被工单切成段，每单有委托方、验收判据、完工时点。⇒ **一张工单 = 一个天然的经历单元**（goal 在前、过程在中间、终态在尾，边界清晰）。这是 zcode 相对芙莉莲（对话漂移、goal 模糊）做经验沉淀的结构优势。

**2. 三方分工**。芙莉莲写需求说明书 → zcode 对照源码审计出勘误 → 殿下拍板 → zcode 施工+验收报告 → 芙莉莲复核、殿下终审。⇒ zcode 既是确认的**接收方**（要被喂全貌）也是**发起方**（要审计工单前提），所以经验体系必须在开工端有"建卡+调取"两个动作。

**3. 两个整理窗口，没有空闲**。zcode 没有 idle 状态（芙莉莲式的"空闲时导入 LLM 拼经历"在这里没有落点），整理只能发生在单的两个边界：**开工前**和**收尾后**。⇒ 体系的两个卡口就卡在这两端。

**4. 判据文化**。一切收口于可复核证据（测试几绿、哈希逐字节、沙箱对拍）。⇒ 经验的取用也要可结算：被召回/被注入/被采用/有效是四件事，分开记账。

**五概念在本体系的落点**（回应架构讨论的分层）：

| 概念 | 职责 | zcode 落点 |
|---|---|---|
| 原始记录 | 保存实际发生了什么 | db.sqlite（只读，不复制不改写） |
| 经历 | 围绕目标组织原始记录 | E 案卷（cases/）+ W 目标卡（orders/） |
| 经验 | 有条件、可行动、可验证的复用建议 | X 条目（lessons/），带 provenance 引用 |
| memory | 跨单保留的状态与约定 | 既有 memories/ 体系（瘦身后） |
| summary | 为用途压缩的视图 | INDEX.md（脚本生成）+ 会话内自动摘要 |
| knowledge | 跨情景规律 | 暂不主动建；同一经验跨三案例验证后再升格 |

## 三、经验复用体系设计（五对象 + 两端卡口 + 四条红线）

### 五对象

```
orders/  W 目标卡   一单一张：goal/范围/验收/来源/终态/session_anchor
cases/   E 案卷    执行证据卷：只认 tool 调用的 state 与产物路径，
                    回复自述不算数；observed 与 inferred 分开标
lessons/ X 经验    可复用条目：适用条件/建议/预期效果/验证点/例外/
                    来源引用/版本历史 —— 一单产出 0..N 条
usages/  U 取用记录 某单采用了哪条经验@哪版：执行了吗/帮上忙了吗/
                    升级还是退役 —— 只对应真实采用，空查询不记 U
queries/ Q 查询记录 每次检索都留账：检索式/命中/空结果判定
                    （空结果也是情报：说明库里没有这类经验）
INDEX.md           reindex.py 生成的总索引（勿手改）
backlog.md         归档兜底待补清单（Stop 钩子自动写）
```

### 两端卡口（信息流）

```
开工端                                    收尾端
/exp.start                               /exp.settle
   │                                        │
   ├─ 0. 建 W 目标卡（含 session_anchor）     ├─ timeline.py 出切单底稿（db 只读）
   ├─ query.py 检索（hit/suspect/drop）      ├─ 按目标三问切单，补 W 终态
   ├─ 逐条对照适用条件                        ├─ 组织 E 案卷（执行证据四元组）
   │   （先验场景存在，再问条件成立）           ├─ 当班主会话内提炼 X 候选
   ├─ 采用项写"冻结规划引用块"进 plan          ├─ 双基准 goal 过滤（见红线②）
   └─ 空结果→记 Q，不算 U，照常开工            ├─ 落盘 X + 回填 Q + 生成 U
                                            └─ verify_chain.py 引用校验
                                               （退出码非零=沉淀失败）
        归档端（兜底）
        Stop 钩子 → settle_check.py：会话结束自动查 W 缺失→backlog
        /exp.archive：人工显式补检（W/E/Q 齐+校验过→可归档）
```

### 四条红线（试跑中被真实问题锤出来的）

1. **本机边界**：经验数据全程不出 `~/.zcode/`；提炼由**当班主会话内**完成——禁止 headless 自调用起第二个模型进程、禁止把底稿/经验正文发给当前会话之外的任何端点。插件本身零网络出口（脚本只有 sqlite 只读+文件读写）。
2. **标题锚过滤（双基准）**：候选经验必须同时与本单 W.goal **和**会话锚（session 标题+首条 goal）有实体交集才入库——单比较切单后的 goal 挡不住漂移单（会话里跑偏出去的杂单会自建目标卡绕过单基准）。漂移单的记录保留在案卷，只是不入经验库；殿下明确批准的目标变更走 `approved_goal_change` 通道。
3. **检索命中资格分级**：打分器里域词（系统名/机制名）命中才算 hit 资格；泛词（"验证""编码""施工"）只给弱重叠分；bigram 词面重叠永不构成命中资格——否则"帮我验证诗歌的编码"会召回变量遮蔽经验（codex 审计实测的反例，已修）。
4. **失败必须可见**：校验器退出码三态（0 全过 / 1 引用缺失 / 2 无引用）——"报告里写了 MISSING 但 exit 0"会让自动流程把失败当成功（也是审计实测，已修）。本体系自己的 E2E 里，我随手编的 6 个假 call 引用就是被它当场全抓的。

## 四、施工手册（每单怎么做）

### 开工（plan 定稿前，跑 /exp.start）

```
/exp.start <本单 goal 一句话>
```
0. **建 W 卡**：orders/W<N>-<日期>-<slug>.md，填目标三问（要解决什么/怎样算完成/来源）、scope、session_anchor、final_state 留空。续单则更新原卡。
1. 跑 `query.py "<goal>"`，看 hit/suspect/drop 三档与得分明细。
2. **逐条对照适用条件**（顺序固定）：先问"本单实际架构里这个场景存在吗"（核数据面走队列还是 DB、真模型还是 mock），再问"条件成立吗"。判定三值：满足/不满足/未知（未知按不满足处理）。
3. 采用的写成**冻结规划引用块**进 plan 的"经验取用"节：引用@版本 / 匹配条件 / 计划变化 / 验证点。执行段不得就地改块；发现不适用走可修订通道（保留旧块→记原因→形成新版块→原授权内继续，越授权则请示殿下）。
4. 空结果：记 Q（不算 U），plan 写"本单无命中"，照常开工。

### 收尾（终态已定，跑 /exp.settle）

```
/exp.settle <session_id>
```
1. timeline.py 出底稿（--full 真全文；error 调用的报错取自 state.error）。
2. 按目标三问切单（一单可能多张 W；拿不准标 pending 不硬编）。
3. 补 W 终态（observed/inferred 分标）。
4. 组织 E 案卷：**只认 tool part 的 state 与产物路径**，工具记录四元组（发起/返回/结果语义——completed≠成功/验证）。
5. **当班主会话内**提炼 X 候选（遵守本机边界三禁）。
6. 双基准过滤 → 过关的落 lessons/X<N>.md（九节正文+版本历史，旧版全文可还原）。
7. 生成 U（采用结算）与 Q 回填。
8. **必跑** verify_chain.py：退出码 0 才算沉淀完成，非零进 backlog。

### 归档（/exp.archive + Stop 钩子自动兜底）

- 人工：`/exp.archive <W编号>` 查 W/E/Q 齐+校验退出码，缺项进 backlog，不阻塞归档、绝不写 db。
- 自动：每次会话结束，Stop 钩子跑 settle_check.py——查该会话有没有 W 卡，缺了自动记 backlog（幂等、探针豁免、fail-open 绝不阻塞收尾）。

### 查账（随时 /exp.query）

- 按 X/W 查取用史与战绩（哪条经验被用过几次、效果如何）；
- 按 session 反查归属（这条会话沉淀了什么）。

### 首次部署（三步 + 验证清单）

```
1. 解包 zcode_experience_plugin_v0.2.0.zip 到 ~/.zcode/plugins-local/experience/
2. config.json 的 plugins.dirs 数组加 "C:\\Users\\<你>\\.zcode\\plugins-local\\experience"
3. 重启 ZCode 客户端
```
验证清单（重启后启动日志 `~/.zcode/cli/log/zcode-<日期>.jsonl` 搜 `plugins.completed`）：

| 计数 | 加载前 | 加载后 |
|---|---|---|
| pluginCount | N | N+1 |
| commandRootCount | n | n+1（/exp.* 四命令） |
| hookCount | h | h+1（Stop 钩子） |
| skillRootCount | s | s+1 |

（本机实测：11→12 / 2→3 / 8→9 / 6→7。）

**跨机部署注意**：四个脚本内的 db 路径（`C:/Users/14538/.zcode/cli/db/db.sqlite`）、经验库路径（`C:/Users/14538/.zcode/experience/`）为本机绝对路径——换机器/换用户名时需改 scripts 里的 `DB_URI`/`EXP`/`LESSONS_DIR` 三处常量；同机重装无此问题。经验库 `~/.zcode/experience/` 不在插件包内（各机各自积累，W/E/X/U/Q 是数据不是代码）。

## 五、实例：体系自己跑通的第一圈（2026-10-12 真实数据）

用「修复本体系自身审计缺陷」这张单当试验田（自举）：

| 环节 | 实况 |
|---|---|
| 开工 | 建 W11 目标卡（真 anchor）；检索 **Q8 空结果**（0 hit）——现有三条经验全是 cowagent/comfytext 域，与插件返工单零交集；如实记 Q 不记 U |
| 执行 | 修复六项审计缺陷（本机边界/退出码/泛词误判/双基准闸/开工建卡/归档钩子） |
| 提取 | X4 入库：「确定性脚本两铁律——命中资格按类型判、失败必须改退出码」（适用条件/验证点/来源引用齐全） |
| 翻车被抓 | 案卷里我随手编了 6 个假 call 引用，verify_chain **当场全抓（exit=1）**——换成 timeline 语义配对的真 id 后 10/10 全过 |
| 复验 | 模拟下张同类单检索「写确定性打分器和校验脚本」→ **X4 hit 8 分**——"下次能查到"成立 |
| 归档 | W/E/Q 齐、校验 exit 0、U 零合法（Q 证明无采用）——归档补检通过 |

这条链同时覆盖了 codex 验收要求的三反例之一（无经验单的真实样本）。

## 六、边界与路线

- **词面检索起步，embedding 后置**：当前 query.py 是域词实体+tags 词面（可解释、零成本）；实测教训（skillwiki：词面 23%、上模型仅 +1.9pp）说明先跑量再决定。新域词往 `DOMAIN_FRAGMENTS` 词典补行。
- **knowledge 层暂不主动建**：同一经验第三次在不同系统被独立验证时再升格，宁缺毋滥。
- **memories 瘦身待做**：INDEX 已超限，分层后 memories 退回纯 memory 层（该工作单独排单）。
- **版本/并发防护靠协议纪律**（版本历史节全文保留），原子写入与版本读取器是后续工程。
- **治理节奏**：每单收尾自然治理（终态回填）；季度级清账（退役过时经验）待试点数据说话。
